# 测试规范

本仓库的测试分**四层**，每层回答的问题不同、能否进 CI 也不同。新人最容易犯的错是把
其中一层当成全部 —— 尤其是**把「静态检查全绿」当成「功能是对的」**。

## 四层，以及各自能回答什么

| 层 | 入口 | 回答的问题 | 花钱 | 进 CI | 现状 |
| --- | --- | --- | --- | --- | --- |
| **单元** | `node --test` | 共用层（`scripts/lib/`）的函数行为对不对 | 否 | ✅ | `test/` 下 5 个文件 |
| **静态** | `./scripts/lint.sh` | 仓库在格式与自洽上有没有问题 | 否 | ✅ | 17 项检查 |
| **端到端** | `node scripts/e2e.js` | **提交出去的东西**能不能跑通全流程 | 否 | ✅（`--offline`）| 6 个环节 |
| **行为** | `node scripts/run-evals.js` | 技能被唤起**之后**干得对不对 | **是** | ❌ | 只对 `git-commit` 可跑 |

**没有第五层。** 「技能到底会不会被唤起」试过，**造不出来** —— 完整证据见
[skills/index.md](../skills/index.md) 的「关于技能唤起的实测」。别再试一遍。

### 各层覆盖不到的东西（要主动知道）

- **静态层**查不出语义错误。比如技能里的命令语法合法但行为不对 ——
  `checks/skill-commands.js` 只做 `bash -n`，它把这句话打在每次运行的输出里。
- **单元层**只覆盖 `scripts/lib/`。`scripts/checks/*.js` 是**可执行入口**，测它们要靠
  端到端层（造故障树、跑真实命令）。
- **端到端层**验的是 `git archive HEAD`，**不是你的工作区** —— 未提交的改动它看不见。
- **行为层**通过**不等于**有效，见下面「消融基线」。

## 验收标准（任何 PR 合并前）

- [ ] `./scripts/lint.sh` 全绿 —— 它已经**包含**单元测试与端到端，不用单独跑
- [ ] CI 全绿（本地全绿**不蕴含** CI 全绿：PR 标题不在本地检查范围内）
- [ ] 改了 `custom/**` 的技能内容 → 跑一次 `node scripts/run-evals.js --skill <名字>`，
      并用 **`--ablate` 复核这条用例有没有区分度**
- [ ] 全仓无 U+FFFD 替换字符
- [ ] 用户可感知的改动 → 记入 `CHANGELOG.md` 的 `[Unreleased]`

## 铁律：任何断言、检查、测试，先证明它能失败

**这条不是形式主义。** 本仓库栽过四次，每次都是「测试全绿但什么都没测」：

| 事故 | 形态 |
| --- | --- |
| 规则 B 的**恒真断言** | 取错了字段（`body` 是 frontmatter 内部的行），而 `metadata.example` 恰好在那个字段里 → 永远通过（15/15）|
| **触发测试** | 改坏三种方式（改描述、删字段、改技能名），它**一次都没红**。那份 15/15 不含任何信息 |
| `skills-doctor` 的**评测** | 3/3 全绿，`--ablate` 一测 **0 条有区分度** |
| `not_contains "git add .env"` | **假通过**：模型**确实执行了** `git -C /private/var/… add .env`，字面匹配漏掉了 |

**怎么证明**：写完之后**把被测对象改坏**（取反一个判断、动一个边界、删掉一段），跑一次
确认**报红**，再改回来。至少对**每一类**断言做一次。

**为什么**：一个不会失败的测试**比没有测试更糟** —— 它让人以为验过了，而且让「红」
变得不可信。

### 消融基线：通过 ≠ 有用

`run-evals.js --ablate` 会把每个用例**不装技能**再跑一遍：

| 装了 | 不装 | 含义 |
| --- | --- | --- |
| ✓ | ✗ | **有区分度** —— 技能确实带来了东西 |
| ✓ | ✓ | **无区分度** —— 用例在测模型本来就会做的事 |

**写用例时怎么才有区分度**：断言那些**不告诉它就大概率不会做**的东西 —— 具体的报告
格式、必须原样引用的路径与名字、项目特有的约定。笼统的「帮我看看 X」几乎必然无区分度，
因为模型自己会看。

## 新检查器的接入清单（五处，缺一不可）

1. `scripts/checks/<名字>.js` —— 用 `lib/report.js` 的 `Report`，退出码 0/1/2
2. `scripts/lint.sh` 的 `CHECKS` 数组
3. `scripts/lint.sh` 的 `dispatch()` case
4. `.github/workflows/ci.yml` 的**同名 job**
5. `.github/workflows/ci.yml` 的 `needs` 列表 / `R_*` 环境变量 / 汇总表里的 `jobs` 数组

第 2 与第 5 步由 `lint-selftest` 断言**集合相等**（比集合，不比数量 —— 同长度互换也会漏）。
加了本地检查却忘了接进 CI，会在 CI 上被抓出来。

**别忘了同步文档里的计数**：`docs/MAINTAINER_GUIDE.md`、`README.md`、`AGENTS.md` 里写着
「N 项检查」「N 个 job」。跑 `node scripts/checks/doc-counts.js --fix` 即可。

## 踩过的坑（测试基础设施特有，每条都真实发生过）

### 目标集 = 「会被提交的文件」，不是工作区

检查器一律通过 `lib/gitfiles.js` 的 `trackedFiles()` 枚举（已追踪 ∪ 未追踪但未被忽略）。
**不要用 `find` / `readdir` 递归**。这条对**文件模式**同样成立：`checks/scripts.js` 检查
入口脚本的可执行位，原先只遍历 git 索引，于是**新加的入口脚本能本地全绿而 CI 报红**
（真实踩过：`run-evals.js` 以 `100644` 提交）。

### 拷贝出来的仓库必须自成 git 仓库

做隔离验证时，`tar` 出来的副本要 `git init && git add -A && git commit`。**没有 `.git`
的副本会让每个检查器直接 `exit 2`** —— 那样无论注入什么都「失败」，断言就成了恒真，
测的是「没有 `.git`」而不是被测的东西。

### 递归：端到端是 lint 的一项，所以它跑 lint 时必须跳过自己

`scripts/e2e.js` 自己也是 `lint.sh` 的一个检查项。它在副本里跑 lint 时要
`--skip e2e`，否则：

```
lint.sh 跑 e2e → e2e 在副本里跑 lint.sh → 又跑 e2e → …
```

### 端到端验的是 HEAD —— 所以脚本与它的接线必须同一次提交

E2E 用 `git archive HEAD` 造副本。**接线（lint.sh / ci.yml）还没提交时，副本里的旧
lint.sh 不认识新检查项的 id**，E2E 会报「未知的检查项」。这是「验证已提交内容」的
必然代价，不是 bug。

### 占位符会让 `bash -n` 误报

技能里的 `git add <resolved-file>`、`npx skills use …@<技能名>` —— bash 把 `<` 当重定向。
不处理就是 7 处里的 6 处误报。**先把成对的 `<…>` 换成普通词再解析**（不成对的 `<` 是
真重定向，不能动）。另外，故意写坏的反例要用 `# skill-check: ignore` **带理由**豁免。

### zsh 的 glob 会让整条命令中止

`for f in .claude/skills/*; do` 在目录不存在时，zsh 报 `no matches found` 并**中断整条
命令**（macOS 默认就是 zsh），于是看起来像「没查到」。**用 `find`**，它对不存在的目录
只是往 stderr 抱怨一句。这条写在 `skills-doctor` 的技能里。

### 变异测试要用 `cp` 备份，不要用 `git checkout --`

`git checkout -- <file>` 会把**未提交的改动一起还原掉**。真实踩过：用一个临时变异验证
检查器，`git checkout` 一跑，整个新写的章节没了。**备份用 `cp`，恢复用 `cp`。**

### 校验与发布必须分成两次调用

写「修正内容 → 校验 → 发布」时别塞进同一个脚本块：某一步失败**不会中止后面的独立命令**，
`&&` 只保护紧邻的那一条。于是「校验挡住了」和「内容发出去了」同时成立。详见
[maintenance/index.md](../maintenance/index.md)。

### 判断成败禁止管道接 `tail` / `head`

```bash
# ✗ 判断的是 tail 的退出码
if gh pr merge N --squash | tail -1; then
```

详细后果见 [maintenance/index.md](../maintenance/index.md)。

## 不要造「不会失败的测试」

这是本文档唯一的**禁止事项**。加一份新的自动化之前，先问：

1. **它可能红吗？** 把被测对象改坏，它会不会报？不会 → 先改到会为止。
2. **它红了说明什么？** 说不清楚 → 它不是检查，是装饰。
3. **它在正确状态下会不会误报？** 会 → 那比没有更糟（训练人忽略输出）。
